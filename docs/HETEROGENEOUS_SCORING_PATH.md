# WNIDIA 提分路径实现文档（P1–P4）

> **范围**：技术侧实现说明。商业与合作分析不在本文档范围。
> **状态**：四个模块**已实现并通过自检**，但**尚未接入主链路**。
> **许可**：Apache-2.0（与仓库整体一致）。

## 背景：为什么做这四项

横向对比同类项目后，暴露出一个关键事实：

> **功能数量没有转化为评分。** 排名靠前的项目功能更少，但有两个共同点：
> ① **接入门槛极低**（调用方零改动）；② **公开了"真跑通"的实测证据**。

因此提分路径不追求"再加更多功能"，而是补这两块短板：

| 短板 | 补法 | 模块 |
|---|---|---|
| 调用方要改造才能用 | 做成透明代理，伪装成对方原本的服务 | **P1** |
| 没有实测证据 | 一条命令产出带标记的验证报告 | **P2** |
| 能力锁死在自有架构内 | 抽成零依赖 SDK，可被第三方采用 | **P3** |
| 计量只是代码不是产品 | 生成可交付账单 | **P4** |

## P1 · 透明代理网关 `proxy_gateway.py`

### 要解决的问题

现有网关要求调用方改用 WNIDIA 的任务接口。但现实是：**已经存在的 agent 与应用
不会为了我们改代码**。

同类项目（家庭/小型集群推理代理）的做法是——**接管调用方本来就在用的端口**，
调用方改个 base_url 就能用。这是它们开发者体验分高的核心原因。

### 设计

```
调用方（零改动）
    │  POST /v1/chat/completions  或  POST /api/chat
    ▼
ProxyGateway
    ├─ infer_feature()   从请求推断任务特征（模型名→容量、文本→上下文、max_tokens→阶段）
    ├─ route()           画像路由（容量/隐私/精度为硬约束）
    ├─ transport()       转发到选中后端的真实端点；失败自动回退次选
    ├─ to_wire()         还原为调用方期望的线格式（这是"透明"的最后一步）
    └─ _record()         按画像计量
```

### 关键实现细节

| 点 | 说明 |
|---|---|
| **双线格式** | OpenAI 与 Ollama 的请求体/响应体互转，调用方感知不到后端差异 |
| **透明端口** | `ollama=11434`、`openai=8000`——调用方连端口都不用改 |
| **特征推断** | 模型名 → 参数量表 → 量化后缀 → 容量（GB）；未知模型返回 0，**不据此拦截** |
| **阶段判定** | 长输入→prefill-heavy；长输出或高并发→decode-heavy |
| **故障回退** | 首选后端失败 → 按候选顺序自动回退；全失败 → 503 且给出原因 |
| **降级安全** | 未接画像时降级为"首个健康后端"，**不影响可用性** |
| **transport 可注入** | 自检注入假传输层，无需网络即可验证逻辑 |

### 自检（18/18）

| 项 | 实得 |
|---|---|
| 高并发/长输出 → 高带宽 5090 | ✅ |
| 大模型 70b-q4（≈38.5GB）→ 仅 GB10 满足 | ✅ |
| 同一模型 fp16（≈140GB）→ 被明确拒绝 | ✅ |
| 隐私请求 → 强制留 privacy-capable | ✅ |
| 首选故障 → 回退次选成功（尝试 2 个） | ✅ |
| 全部故障 → 503 不崩溃 | ✅ |
| OpenAI / Ollama 线格式还原 | ✅ |
| 未接画像 → 降级可用 | ✅ |
| 计量按画像差异化 | ✅ 5090 与 GB10 金额不同 |

### 已知限制（不掩饰）

1. **流式（stream=true）目前是"合并返回"**：聚合后一次性产出，语义不丢但**没有真正流式体验**。真实流式需逐块转发，列为后续项。
2. `MODEL_PARAMS_B` 是参考表；未知模型不臆断容量。
3. 自检跑通的是**逻辑**——假传输层不代表真实网络。

## P2 · 真机验证 runner `live_verify.py`

### 要解决的问题

排名高于我们的项目，功能远少于我们，但它**公开了在三台真实机器上跑通某模型的
实测结果**。评审看到的是证据。

本模块：**一旦有真机，一条命令产出可公开报告**。

### 测什么

| 指标 | 含义 |
|---|---|
| P50 / P95 时延 | 真实端到端分布（**不是决策质量**） |
| ok_rate | 成功率 |
| tokens/s | 实测吞吐 |
| 路由命中 | 画像路由 vs 基线（固定首节点） |
| 成本 | 按画像计量的实测金额 |

### 场景矩阵

| 场景 | 配置 |
|---|---|
| `small-chat` | 7b / 200 ctx / 128 out / 并发 1 |
| `long-context` | 7b / 8000 ctx / 128 out / 并发 1 |
| `high-concurrency` | 7b / 500 ctx / 512 out / **并发 8** |
| `large-model` | 70b-q4 / 500 ctx / 256 out / 并发 1 |

### 诚实设计（最关键）

```
transport 注入假传输层  →  结果标记 simulated=True
                        →  报告顶部写"模拟数据，不可对外发布"
默认真实 HTTP 传输层     →  才是可用于对外的实测数据
```

且上游不返回 usage 时，token 数按字符折算并标记 `estimated=True`，
**不伪造真实 token 数**。

### 自检（18/18）

统计正确性（P95≥P50、token 汇总、吞吐）、估算标记、失败处理、
矩阵覆盖、A/B 双方节点、报告含模拟标注、空输入不异常。

## P3 · 零依赖路由内核 `routing_sdk.py`

### 要解决的问题

同类项目公开把"更聪明的路由"列为最清晰的 roadmap 项——并自述当前调度
**不看 GPU 型号、不看显存、不看利用率、不看时延**。

这正是 WNIDIA 已实现的能力。但能力锁在自有架构里，别人用不上。

### 设计约束：零依赖

**只依赖标准库**，不 import WNIDIA 任何模块。已实测：单独复制到空目录仍能全过。

这样才能：
- 第三方**直接复制**使用（不必先接受 WNIDIA 架构）
- 或**向上游贡献**（贡献时不引入整套依赖）

### API

```python
from routing_sdk import DeviceSpec, RequestSpec, recommend

r = recommend(devices, RequestSpec(model_size_gb=14, concurrency=32))
# → {'ok': True, 'node_id': 'h100-0', 'bottleneck': 'bandwidth',
#    'reason': '...', 'ranking': [...], 'excluded': {...}}
```

| 特性 | 说明 |
|---|---|
| **硬约束优先** | 容量 / 隐私 / 精度不满足直接排除，**不参与打分** |
| **可解释** | 返回 `reason` + 完整 `ranking` + `excluded`（含排除原因） |
| **确定性** | 同输入必同输出（无随机、无时间依赖） |
| **鸭子类型** | `DeviceSpec.from_any()` 可从任意同名属性对象构造——第三方对象零改造 |
| **纯 dict 入口** | `recommend_from_dicts()` 便于配置化/跨语言 |

### 自检（17/17）

四类瓶颈识别、路由正确性（容量/隐私/精度/拒绝）、排序与确定性、
空池与非法参数、**鸭子类型适配**、dict 往返、dict 入口。

## P4 · 计量账单与审计链 `metering_report.py`

### 要解决的问题

计量是横向对比中 WNIDIA **唯一明显领先**的一项。但"有计量代码"不等于"有计量产品"——
**评审看不到账单，就等于没有**。

### 能力

```
用量记录 → 账单（按租户/项目/节点）
        → 三种导出（Markdown / CSV / JSON）
        → 哈希链（可验证记录未被事后修改）
        → 反事实对比（若全跑在某张卡上要花多少 → 量化编排省了多少）
        → 单位成本（¥/千 token，用于跨平台比价）
```

复用现有模块，不重写：`tenant_metering.UsageRecord/aggregate` +
`profile_metering.meter`（按画像成本系数 + 能耗）。

### 诚实设计

1. 账单带 `cost_factor_placeholder=True`——**明确标记单价为占位值**，
   须由真实采购/折旧/电价替换后才能用于结算。
2. 哈希链只保证"记录未被事后修改"，**不等于第三方认证**。
3. `estimated=True`（token 为估算）的记录单独计数并透传，不与真实 usage 混淆。

### 自检（18/18）

分组正确、合计=明细之和、估算计数、占位标记、单位成本、
反事实对比、**篡改第 2 条能被哈希链检出**、三种导出、空账单、按租户筛选。

## 四模块与现有架构的关系

```
                     ┌─────────────────┐
   调用方（零改动） ─▶│ P1 透明代理网关  │
                     └────────┬────────┘
                              │ 任务特征
                     ┌────────▼────────┐
                     │ 画像路由（②）    │◀── P3 零依赖内核（可独立分发）
                     └────────┬────────┘
                              │ 选中节点
                     ┌────────▼────────┐
                     │ 后端真实推理服务 │
                     └────────┬────────┘
                              │ usage
                     ┌────────▼────────┐
                     │ 按画像计量（③）  │
                     └────────┬────────┘
                     ┌────────▼────────┐
                     │ P4 账单 + 哈希链 │
                     └─────────────────┘

   P2 真机验证 runner：横向观测上述链路，产出实测报告（不介入调度）
```

**横向关系：P2 观测、P1 接入、P3 分发、P4 呈现。互不耦合，可单独使用。**

## 接入步骤（等真机就绪）

| 步骤 | 动作 |
|---|---|
| 1 | 把 15 个模块放入 `controller/` |
| 2 | 用 `device_discovery` 自动注册设备画像（或手工注册） |
| 3 | P1 起在透明端口（11434 / 8000），**替换 transport 为默认真实 HTTP** |
| 4 | P2 跑 `run_matrix()` + `ab_compare()`，**确认报告无 simulated 标记** |
| 5 | P4 生成账单（替换成本系数为真实值后） |
| 6 | 按 `HETEROGENEOUS_CHECKLIST.md` 做 M2 接入与 T1–T10 |

---

## 必须守住的边界

1. **P1/P2 的自检跑通的是逻辑**，假传输层不代表真实网络。
2. **P2 报告带 `simulated=True` 时不得对外发布**。
3. **P4 账单在成本系数替换前不得用于结算**。
4. **四个模块均未接入主链路**，不得表述为"已生效"。
5. P3 虽零依赖可分发出去，但**权重仍是保守初值**，需实测调优。
