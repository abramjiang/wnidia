# v4 三轮 bug 自查报告

> 本文件是**当前版本（v4）**的排查报告；v3 的历史记录见
> `docs/BUG-HUNT-3ROUNDS-v3.md`。
>
> 前提：**先让检查手段本身可信，再去检查代码**。否则会出现 v3 那种
> "全绿但其实是假绿"的情况。因此本报告在第 1 轮之前先做了一遍"评测地基"复核。

范围：`wnidia_v4` 全仓（controller / worker / agent / skills / scripts / tests / bench / sdk）
方法：① 编译与静态分析（`compileall` + `pyflakes`）→ ② 沙盒端到端冒烟
（`scripts/sandbox_v4.py`，A–M 全能力）→ ③ 边界与对抗
（`tests/adversarial_test.py` 扩充 J–R + `run_evals` 全量技能评测）

## 第 0 轮 · 评测地基复核（先修工具，再修代码）

| 编号 | 现象 | 根因 | 影响 | 修复 |
|---|---|---|---|---|

## 第 2 轮 · 沙盒端到端冒烟（`sandbox_v4.py` A–M）

这一轮抓到的都不是"写错符号"，而是**设计与断言层面的错**。

| 编号 | 严重度 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| **B4-09** | **高** | 场景 B1：任务提交后**卡在 running 整整 60s**，最终 504 | 就是 B4-02。控制面 `poll_running()` 调 worker `/status` 拿到 500，`except` 静默 `continue`，任务永远不终态 | 修 B4-02；沙盒 B1 现在断言 HTTP 200 且能取到完成体 |
| **B4-10** | 中 | 场景 B2：断言"命中节点时延 ≤ 预算"随机失败 | **断言本身不成立**：时延每个心跳都在变，任务结束后读的是"当前值"，不是"决策时的值" | 改为核对 bind 事件里记录的**决策时时延**；bind 事件精度从 0 位小数提到 1 位 |
| **B4-11** | 中 | 场景 B3：用"最小实测时延 ÷ 2"构造不可满足预算，偶发任务正常完成 | 竞态：某次心跳可能低到阈值以下 | 改用 `0.001ms`（低于上报精度 0.01ms，构造上不可能满足） |
| **B4-12** | **高** | 场景 C1/C2：SLA 优先级排队**必然测不出来** | **用例设计错**：网关是同步的（提交后阻塞直到完成），连发两次 `chat` 不可能让两个任务同时排队 | 新增演示注入端点 `/admin/inject/queue`（同批落库），并重写场景 C 为"后创建的高优先出队" |
| **B4-13** | 中 | 同批入队的两个任务可能被拆到两个调度节拍 | `db.upsert_task` 逐条加锁，调度循环在另一线程，可插入 | 新增 `db.upsert_tasks()`：**单锁单事务**批量写入 |

## 第 3 轮 · 边界与对抗

| 编号 | 严重度 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| **B4-14** | **高** | 沙盒 J5「审计链完整」失败：`broken=[{seq:20, why:'chain_hash 不匹配（内容被改）'}]` —— **审计链自己把自己判成被篡改** | `db.append_chain()` 调用了**两次** `now_ms()`：一次参与哈希、一次写入 `ts` 列，跨毫秒即不一致。另外 `chain_head()` 与 `_insert()` 是两次独立加锁，"读链头→落库"可被插入，高并发下会产生**真分叉** | 单次取时间戳并让哈希与落库共用；`chain_head → 算哈希 → _insert` 全程持同一把可重入锁，保证原子 |
| **B4-15** | 中 | 对抗 J2：`POST /admin/inject/queue` 传 `need_mem_gb="abc"` → **HTTP 500** | 请求体声明成 `List[dict]`，处理时直接 `int()/float()` 强转用户输入 | 改成显式 pydantic 模型（类型错误统一 422）+ 取值范围夹取，并把"被改写的字段"回给调用方 |
| **B4-16** | 中 | `POST /admin/qpu/submit` 传 `circuit="abc"` 或含非 dict 元素 → **HTTP 500** | `qpu.submit()` 只捕获 `ValueError / TypeError`，字符串走进去抛的是 `AttributeError` | 先做电路形状校验（必须是门对象数组），并把捕获范围扩到 `KeyError / AttributeError / IndexError` |
| **B4-17** | 中 | 对抗测试 J2 拿到 500 之后，**J3 直接让整个测试进程崩掉**（`Connection reset by peer`） | 服务端在未处理异常后会关闭这条 keep-alive 连接；测试复用了池化连接，而 requests **默认不对 POST 重试** → 真实断言结果被掩盖，看起来像"被测服务挂了" | `tests/_clean.py` 新增 `robust_session()`：只在**连接层**重试（建连失败 / 连接被重置），**不重试任何状态码**；且**超时原样抛出**（有用例故意用短 timeout 靠 `ReadTimeout` 继续跑） |
| **B4-18** | **高** | 对抗 M9：同一天连续执行两次结算，`records 2 → 4` —— **机主分成被算了两遍** | `settlement.settle()` 的 docstring 明写"同一 period + node 先清后写"，但实现里**只有插入、没有清理**（承诺写在文档里，动作没写进代码） | 新增 `db.clear_settlements(period)`，`settle()` 改为"先清后写"，并在事件与返回里报出 `overwritten_records`（覆盖了多少条旧记录） |

> 这几条里有两条是"**没崩但也不该给 500**"（脏输入必须是 422 或明确拒绝），
> 一条是"**功能全对、只是账算了两遍**"——后者最危险，因为它不报错。

对抗测试新增覆盖（`tests/adversarial_test.py`，J1–R22）：

- J 批量入队非法入参：空列表 / 非法 sla + 非数值 / 缺 `tasks` 字段
- K 断网批次回放：**幂等**（同 `batch_id` 重复只计一次）、缺 `batch_id` → 422、控制面计入补偿
- L 门槛：五条齐全、样本不足**不判 GO**、每条都报样本量
- M 结算：重复执行**不产生重复记录**、分成比例显式标注为规划假设
- N QPU：超上限量子位 / `cudaq` 未安装（拒绝而非静默回退）/ 未知门
- O 机队：未注册机型灰度不崩 / 非法灰度比例被拒 / 未注册机器人回传不 500
- P 分时：时片大于窗口被拒 / 零窗口被拒
- Q 容错：非法 `secret` / 非法 `cc_required` 不打断闭环
- R 审计：证据包签名可校验、**篡改可检出**、默认不含 prompt 明文

### 本轮最值得记住的三条

1. **B4-02（漏 `progress_pct()`）**：一个"少写一个方法"的错误，把三个端点打成 500，
   而控制面用 `except: continue` 把它吞掉，表现为"任务卡住"而不是"端点报错"。
   教训：**轮询失败必须留下痕迹**。

2. **B4-14（审计链双取时间戳）**：这是"看起来最不可能出错"的地方——哈希链的核心
   不变量被一个多余的函数调用破坏。它不会让任何功能失效，**只会在校验时随机地把
   自己判成被篡改**。教训：凡"计算摘要 → 落库"的路径，必须用**同一个值**做两件事，
   且"读状态 → 算 → 写"必须原子。

3. **B4-18（结算承诺写在文档、动作没写进代码）**：docstring 写明"先清后写"，
   代码里却只有插入。它**不报错、不崩溃、界面正常**，只是钱算错一倍。
   教训：涉及钱与额度的"幂等"必须有对应的**写动作**（清/覆盖）与可观测证据
   （本例在事件与返回值里报出覆盖了多少条），不能只写成注释。
